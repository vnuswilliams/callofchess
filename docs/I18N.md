# Guide des traductions

Les traductions statiques de l’interface sont versionnées avec le code source dans `client/src/locales`. Elles sont chargées côté client par `client/src/contexts/LanguageContext.tsx` et ne nécessitent aucune requête Supabase.

> **Règle générale :** l’interface statique va dans les fichiers JSON ; le contenu dynamique administrable, comme une leçon créée depuis Supabase, reste dans la base de données.

## Organisation des fichiers

Chaque langue possède les mêmes domaines fonctionnels et les mêmes clés. La structure actuelle est la suivante :

```text
client/src/locales/
├── fr/
│   ├── common.json
│   ├── auth.json
│   ├── chess.json
│   ├── lessons.json
│   ├── profile.json
│   └── settings.json
└── en/
    ├── common.json
    ├── auth.json
    ├── chess.json
    ├── lessons.json
    ├── profile.json
    └── settings.json
```

Les fichiers sont regroupés par domaine plutôt que dans un fichier unique. Utilisez `common.json` pour les libellés partagés par plusieurs pages, puis le domaine le plus précis pour les textes propres à une fonctionnalité.

| Domaine | Utilisation recommandée |
| --- | --- |
| `common.json` | Navigation, boutons, états généraux, apparence et libellés transversaux |
| `auth.json` | Connexion, inscription, récupération de compte et déconnexion |
| `chess.json` | Vocabulaire de l’échiquier et des positions |
| `lessons.json` | Libellés de parcours et d’exercices |
| `profile.json` | Profil, badges et historique |
| `settings.json` | Réglages et préférences |

## Ajouter une nouvelle clé

### 1. Choisir le domaine

Déterminez d’abord où la clé doit vivre. Un libellé utilisé par plusieurs pages appartient généralement à `common.json`. Une chaîne spécifique à une page ou à une fonctionnalité doit être ajoutée au domaine concerné.

### 2. Ajouter exactement la même clé dans chaque langue

Les clés sont stables et doivent être identiques dans tous les fichiers de langues. Par exemple, pour ajouter le bouton « Enregistrer » :

```json
// client/src/locales/fr/common.json
{
  "save": "Enregistrer"
}
```

```json
// client/src/locales/en/common.json
{
  "save": "Save"
}
```

Dans un fichier existant, ajoutez la propriété en respectant le format JSON : guillemets doubles, virgule entre les propriétés et aucune virgule après la dernière propriété.

### 3. Utiliser la clé dans React

Un composant React doit récupérer `t` depuis le contexte de langue et utiliser la clé plutôt que le texte directement :

```tsx
import { useLanguage } from "@/contexts/LanguageContext";

export function SaveButton() {
  const { t } = useLanguage();

  return <button type="button">{t("common.save")}</button>;
}
```

Pour les clés du domaine `common`, l’appel court `t("save")` reste accepté. La forme explicite `t("common.save")` est recommandée dans le nouveau code, car elle rend le domaine visible et facilite la maintenance.

Les clés imbriquées sont également supportées :

```json
{
  "account": {
    "title": "Mon compte"
  }
}
```

```tsx
<h1>{t("common.account.title")}</h1>
```

Évitez de construire une clé à partir d’un texte affiché. Une clé doit rester stable même si sa traduction est reformulée.

## Ajouter une nouvelle langue

L’ajout d’une langue comporte quatre étapes : créer les fichiers JSON, les importer dans le contexte, déclarer le code de langue et adapter le contrôle de changement de langue.

### 1. Créer le dossier et recopier les domaines

Pour ajouter l’espagnol, créez :

```text
client/src/locales/es/
├── common.json
├── auth.json
├── chess.json
├── lessons.json
├── profile.json
└── settings.json
```

Recopiez toutes les clés existantes depuis `client/src/locales/en/`, puis traduisez uniquement les valeurs. Ne renommez pas les clés et ne supprimez pas un domaine existant.

### 2. Importer les fichiers dans `LanguageContext.tsx`

Ajoutez les imports espagnols :

```tsx
import esCommon from "@/locales/es/common.json";
import esAuth from "@/locales/es/auth.json";
import esChess from "@/locales/es/chess.json";
import esLessons from "@/locales/es/lessons.json";
import esProfile from "@/locales/es/profile.json";
import esSettings from "@/locales/es/settings.json";
```

Ajoutez ensuite la langue au type et aux ressources :

```tsx
export type Language = "fr" | "en" | "es";

const resources: Record<Language, TranslationTree> = {
  fr: { common: frCommon, auth: frAuth, chess: frChess, lessons: frLessons, profile: frProfile, settings: frSettings },
  en: { common: enCommon, auth: enAuth, chess: enChess, lessons: enLessons, profile: enProfile, settings: enSettings },
  es: { common: esCommon, auth: esAuth, chess: esChess, lessons: esLessons, profile: esProfile, settings: esSettings },
};
```

Le `Record<Language, TranslationTree>` permet à TypeScript de signaler une langue déclarée mais absente des ressources.

### 3. Mettre à jour la langue mémorisée et le sélecteur

Le contexte actuel mémorise la langue dans `localStorage` sous la clé `echequier-language`. Après l’ajout d’une langue, vérifiez que la lecture de cette valeur accepte son code et qu’une valeur inconnue revient à la langue par défaut.

Le bouton actuel alterne entre deux langues. Pour trois langues ou davantage, remplacez l’alternance par un sélecteur explicite, par exemple un `<select>` ou un menu, et appelez `setLanguage("es")` lorsque l’utilisateur choisit l’espagnol. Les codes utilisés par `document.documentElement.lang` doivent correspondre aux codes BCP 47 attendus par le navigateur, par exemple `fr`, `en` ou `es`.

### 4. Ajouter les traductions des contenus spécifiques

Les données pédagogiques statiques qui possèdent déjà une forme par langue, par exemple `{ fr: ..., en: ... }`, doivent être complétées avec la nouvelle langue ou migrées vers les fichiers JSON si elles deviennent des chaînes d’interface partagées. Les contenus créés dynamiquement et administrables peuvent rester dans Supabase.

## Fallback et traductions manquantes

La fonction `t()` applique le fallback suivant :

1. la clé dans la langue sélectionnée ;
2. la même clé en anglais ;
3. la clé sans le préfixe `common.` lorsque l’appel utilise la forme courte ;
4. le nom de la clé lui-même si aucune valeur n’est disponible.

Une traduction manquante ne doit donc pas provoquer de crash. Elle doit toutefois être corrigée avant publication : l’affichage du nom de clé est un signal de maintenance, pas une traduction acceptable pour l’utilisateur final.

## Vérification avant commit

Après toute modification de traduction, exécutez les commandes suivantes depuis la racine du dépôt :

```bash
python3 scripts/verify_locales.py
pnpm check
pnpm test -- --run
pnpm build
```

Le script `scripts/verify_locales.py` vérifie que les deux langues possèdent les mêmes fichiers et les mêmes clés. Il doit être étendu si une règle supplémentaire de validation est nécessaire, par exemple la détection des valeurs vides.

Vérifiez également les points suivants :

| Contrôle | Attendu |
| --- | --- |
| Parité des domaines | Chaque langue possède les mêmes fichiers JSON |
| Parité des clés | Chaque fichier possède exactement les mêmes clés |
| Code React | Aucun nouveau texte statique traduisible n’est écrit directement dans le JSX |
| Données dynamiques | Les leçons ou données administrables restent dans leur source métier prévue |
| Fallback | Une clé absente ne fait pas planter l’application |
| Persistance | Le changement de langue reste conservé après rechargement |
| Interface | Les pages principales sont vérifiées en français et en anglais, sur desktop et mobile |

## Ce qu’il faut éviter

N’enregistrez pas les traductions statiques dans Supabase et n’ajoutez pas de requête réseau pour récupérer un libellé d’interface. Ne créez pas de clé différente selon la langue : `checkmate` doit rester `checkmate` en français comme en anglais. Ne regroupez pas toutes les traductions dans un fichier gigantesque et ne laissez pas une langue avec des clés absentes de l’autre.

Enfin, ne traduisez pas automatiquement une donnée dynamique qui doit rester administrable. La séparation attendue est la suivante :

> **Interface et contenu statique** → fichiers JSON versionnés → déploiement avec l’application.
>
> **Contenu métier dynamique** → source de données applicative, notamment Supabase lorsque cela est prévu.
